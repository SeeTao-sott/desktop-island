# 灵动岛 · 阶段 0 计划

## 本机现状（2026-10-15 检查）
- Windows 11 Home 26200；主屏 1920x1080 @125% 缩放（逻辑 1536x864）
- 已有：Node v24.14.0 / npm 11.9.0、Git 2.53、WebView2 155、nvidia-smi（驱动 596.49，GTX 1650 可读温度）、winget
- 没有：Rust、VS C++ 生成工具（MSVC + Windows SDK）、.NET SDK
- 磁盘：C 盘剩 35.2 GB，D 盘剩 34.2 GB
- 媒体会话最小测试：已通过（PowerShell 直接调 GlobalSystemMediaTransportControlsSessionManager，读到 Chrome/YouTube 的歌名、歌手和播放状态）

## 技术选型
| | Tauri 2 | Electron | C# WPF |
|---|---|---|---|
| 动画丝滑 | WebView2(Chromium) GPU 合成，CSS transform/opacity 稳 60fps | 同为 Chromium，一样顺 | 透明窗口(AllowsTransparency)走软件渲染，大窗口动画易掉帧 |
| 透明 + 点击穿透 | transparent 窗口 + set_ignore_cursor_events，配合 Rust 侧光标位置判断 | 支持，setIgnoreMouseEvents(forward) | 支持，需 Win32 互操作 |
| 系统接口 | Rust `windows` crate 直接调 WinRT/Win32 | 需要原生模块(node-addon)，麻烦 | 原生最方便 |
| 资源占用 | 空闲约 60–120MB，安装包几 MB | 150–300MB，包 80MB+ | 50–100MB |
| 结论 | **推荐** | 太重 | 动画是短板 |

## 关键设计
- 窗口固定为展开后的最大尺寸、全透明、置顶、无边框、不进任务栏；胶囊变形只在网页里做
- 弹簧动画：自写弹簧物理（rAF），动画结束后立刻停止循环，空闲零重绘
- 点击穿透：窗口默认穿透；Rust 侧低频读光标位置(GetCursorPos，不是钩子)，光标进入胶囊范围才接收鼠标
- 全屏检测：SHQueryUserNotificationState + 前台窗口尺寸比对，只读查询，不注入任何进程
- 不监听键盘，不挂全局钩子

- 安装备注：VS Build Tools 用的是 2026 版(18.x)，2022 版安装器已被微软拒绝

# 侧边架子

## 阶段 0 调查（2026-10-15）
- 桌面在 OneDrive 里：C:\Users\User\OneDrive\桌面（已开桌面备份；当时 OneDrive 没在运行）
- 架子文件夹定在 C:\Users\User\OneDrive\架子：同盘移动、继续云端备份
- 桌面 20 项 + 公共桌面 6 项（普通权限就能移动，本机只有一个账户）；两个文件夹整个放进「其他」
- 拖出：Shell 拖拽（SHCreateShellItemArrayFromIDLists → BHID_DataObject → SHDoDragDrop），独立进程的 Chromium 上传框收到正确文件名、大小、内容
- 拖文件时前台线程的鼠标捕获窗口是 CLIPBRDWNDCLASS；拖滚动条时是浏览器自己的窗口 → 用来区分

## 阶段 1 实测（2026-10-15）
- 同一个程序里的第二个窗口（shelf.html），共用 tokens.css / motion.ts（颜色、玻璃、弹簧参数）
- 误触测试全部通过：快速经过边缘、沿边缘上下滑、停在右上角关闭按钮 / 右下角、按住浏览器滚动条停在触发区 2 秒、点最大化窗口的关闭按钮
- 拖着文件到右边缘 0.5 秒内滑出，文件在面板上时不收回
- 快捷键 Ctrl+Alt+D（RegisterHotKey）：打开后可直接打字搜索；再按一次 / Esc / 点别处都会收回，焦点还给原窗口
- 修正 1：架子窗口一显示就抢走前台焦点 → 平时不可聚焦，滑出后才可聚焦
- 修正 2：第一次滑出有一帧 48ms → 启动时隐形预渲染一次，之后 145fps、最慢一帧 7ms
- 修正 3：焦点移进网页时会先报"失去焦点"导致刚打开就收回 → 150ms 后确认前台确实换了才收回
- 全屏时架子窗口一起隐藏，游戏里推鼠标到边缘不会弹出
- 占用（灵动岛 + 架子）：空闲 CPU 约 0.07%（加 nvidia-smi 约 0.16%），内存 144 MB

## 阶段 2 实测（2026-10-15）
- 文件安全：fileops.rs 集中处理。不带"覆盖"选项移动；同盘直接移；跨盘复制 → 逐字节比对 → 再删原件；出错时只清理自己复制出来的半成品，原件不动；被占用时用重启管理器说出程序名
- 自动测试 6 个全部通过（cargo test）：分类规则、危险路径拦截、重名自动编号且不覆盖、跨盘移动单文件和文件夹、被占用的文件不移动。跨盘测试还抓出了一个真 bug（单个文件跨盘时目标路径多了个 \）
- 拖放接收：Tauri/WebView2 自带的接收在"先隐藏再显示"的窗口上没注册上 → 改为自己在架子子窗口上注册 IDropTarget；跨进程拖放回调里不能直接给网页发消息（同步输入调用），改成排队后在界面线程发
- 自动化工具按住鼠标时会在光标旁显示提示浮窗，松手会落在浮窗上导致拖放被取消 → 拖入的最后一步需要人工用资源管理器测
- 界面实测通过：自动刷新（系统通知，不轮询）、系统图标 / 图片缩略图（要显式请求 THUMBNAILONLY）、PDF 图标（图标改为专用 STA 线程取）、右键菜单、移到其他分类 + 撤销、F2 改名重名自动编号、Delete 移到「已移除」、文件被占用提示"正在被 Windows PowerShell 使用"、在资源管理器中显示并选中、双击打开
- 日志：%APPDATA%\com.stanley.desktopisland\shelf-log.jsonl，每次移动一行
- 占用：空闲 CPU 约 0.04%，内存 142 MB

## 阶段 2 补充修正（2026-10-15）
- 拖着文件推到边缘、架子刚滑出时"禁止/复制"随机：WebView2 的子窗口属于浏览器进程，内核会把自己的拖放目标注册回去，和我们的互相覆盖 → 改为拖文件经过架子时在面板上盖一个我们自己的隐形窗口（透明度 1/255）接住拖放，拖完就拿掉。用户实测多次都正常
- 没用 WebView2 自带拖放的原因：它会把快捷方式解析成目标程序的路径，架子会去搬程序本体
